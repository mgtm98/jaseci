- **js_engine replaces Bun as jac's JavaScript runtime, built into the binary**: `jac/js_engine/` holds a Node.js-compatible JavaScript engine written in Jac. `zig build` links it into `libjs_engine.so` with the in-repo compiler, beside `libjs_native.so` (its C shims, PCRE2, libuv, nghttp2, llhttp, brotli and ICU, compiled by Zig from `build.zig.zon` pins), the pinned Wasmtime C API and the precompiled builtins, and ships them as the runtime's `js/` directory: nothing beyond glibc comes from the system, and every step is cached by the Zig build (`zig build js-engine` builds just the engine). The engine is not a separate program: the `jac` binary invoked as `node` (the runtime's `js/bin/node` link) runs it in-process, which is how Vite, the cl test runner, `jac x` and npm scripts execute, and `jac install --npm` and the client build's dependency sync call its package manager in-process. The pinned Bun download (`zig build fetch-bun`, `payload fetch-bun`, `--bun=`, `JAC_BUN`) is gone, as are `JAC_JS_ENGINE` and the PATH and checkout lookups. A Jac shared library whose root module has an entry now exports it as `jac_main(argc, argv)`, `jac build --native --lib` exports only the root module's `:pub` surface (its imports' `:pub` symbols stay internal, so the whole-program optimizer treats them like an executable's), and the native linker's static-archive floor selects members across archives, so a library that needs another (libssl needing libcrypto) links.
